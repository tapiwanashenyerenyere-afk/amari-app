01 / Executive Frame

Richly held. Austerely revealed.

The research says AMARI is not just building an app. It is building a trusted, premium diaspora resource graph where the data is valuable because it is handled with restraint.

The one-sentence strategy

Make the client reveal as little as possible. Make the server decide everything important. Make data hard to correlate. Make privileged access rare. Make onboarding useful in aggregate but low-risk in raw form.

What this deck helps you decide

  • How hard the first authentication chain should be.
  • Which AMARI archetype graph best balances richness and shipping speed.
  • Which three onboarding questions should seed product-market fit and investor proof.
  • How much hardening to ship before wider invite distribution.

Founder lens

Every decision is a tradeoff between trust, friction, speed, and data quality. The correct answer is not always the most complex answer.

Security makes the data hard to take. Onboarding makes the data worth holding. They are the same project.

02 / Research Inputs

The five source streams are saying different things, but they converge on one system.

The master synthesis blends security standards, privacy law, mobile hardening, onboarding design, and investor narrative into one implementation brief.

D1

OWASP MASVS L2 + RESILIENCE, six-axis archetype model, Frequencies -> Absences -> Standards question flow, investor/sponsor language, 14-day sprint.

D2

NIST framing, passkeys, two-axis archetype model, privacy planes, attestation response model, role/stage/90-day essential questions.

D3

Privacy-conscious diaspora resource graph, tone variants, data model, confidence scoring, benchmark review across premium and network communities.

D4

Four-plane architecture, evidence-ledger resource graph, Expo/Supabase code references, event taxonomy, resource activation as north-star metric.

D5

Vibe-coded app risks: RLS gaps, SecureStore size gotchas, OTA code-signing, MobSF/Frida/Objection/Burp pentesting, React Native bundle patching.

What they agree on

The app must assume the client can be hostile, the server must enforce authorization, onboarding must collect structured signals without feeling extractive, and external reporting must remain aggregate-only.

What they disagree on

The sources disagree mostly on degree: passkeys now or later, two-axis or six-axis archetype, simple card questions or richer standards sliders, native attestation only or RASP too, and simple storage versus an evidence ledger.

03 / Settled Commitments

These are not open decisions. They are the security and privacy floor.

Server decides

  • Every public API table needs RLS enabled at creation.
  • No service-role key can ever touch the mobile binary.
  • Security-definer functions must lock `search_path`, validate `auth.uid()`, and revoke public execute.

Secrets stay secret

  • Invite codes are high-entropy secrets, hashed at rest and single-use.
  • Mapbox `sk.` token is server-only; client gets restricted `pk.` only.
  • EAS Update must be code-signed before relying on OTA updates.

Privacy by design

  • No raw invite codes, magic links, tokens, emails, graph coordinates, or free-text onboarding answers in logs.
  • Australian Privacy Principles apply, especially APP 3, 5, 6, 11, 12, and 13.
  • Investor and sponsor reporting is aggregate-only with k-anonymity thresholds.
Area Settled Position Why It Matters
OAuth PKCE on mobile flows Prevents implicit/browser redirect weaknesses; auth code is one-time and short-lived.
Storage SecureStore for refresh token/device secrets AsyncStorage and plain persisted caches are too easy to extract from compromised devices.
Onboarding Invite -> email -> graph -> 3 cards -> consent recap All product-side sources converge on this flow. The open question is how rich each step should be.
Reporting No member-level rows to partners AMARI's premium trust position depends on never turning members into a drill-through dataset.

05 / Architecture

The recommended data architecture is separated by blast radius.

The synthesis recommends D4's four-plane model plus reporting and audit because it gives Codex concrete tables and it prevents one feature surface from becoming a full identity leak.

Identity

Email hash, invite metadata, account status, consent version. Server-only access.

Profile

Display profile, archetype, stage, offer/ask. Member self-read/write under RLS.

Graph

Resource signals and member edges. Evidence ledger, service-written, selectively visible.

Analytics

Pseudonymous event facts and daily snapshots. No email, no raw identity.

Reporting

Partner aggregates only. Minimum cohort thresholds. No drill-through.

Audit

Export requests, privileged reads, admin actions. Hash-chained and restricted.

Implementation implication: do not build onboarding as "just profile fields." Build it as the first event that seeds a privacy-safe resource graph.

07 / Decision 1: Auth Chain

How much authentication friction should AMARI impose at launch?

Option A

Email OTP + biometric step-up + MFA by tier

Traditional security posture. Email stays primary, biometrics protect sensitive actions, TOTP becomes mandatory for Laureate and Platinum members.

Upsides and downsides
  • Upside: strongest near-term control without waiting for passkey maturity.
  • Upside: aligns well with high-value member tiers and sensitive actions.
  • Downside: adds UX friction and recovery complexity early.
  • Downside: email remains phishable and can be compromised.
Option B

Email bootstrap -> passkeys as trust anchor

Email verifies the user once, then the member creates a passkey. Long-term auth becomes phishing-resistant.

Upsides and downsides
  • Upside: strongest long-term account security and best NIST-aligned direction.
  • Upside: reduces reliance on email magic links over time.
  • Downside: Supabase passkey support needs current verification before commitment.
  • Downside: passkey education and recovery can confuse early users.
Option C

PKCE email OTP only for MVP

Lowest-friction launch path. Email verification via Supabase PKCE, then onboarding immediately.

Upsides and downsides
  • Upside: fastest to ship and best for TestFlight/Play Store onboarding validation.
  • Upside: aligns with the intended flow: invite -> email -> graph.
  • Downside: weaker against email compromise and SIM/email account takeover.
  • Downside: sensitive actions still need later step-up controls.
Recommended decision: Phase 1 uses Option C so onboarding ships. Phase 2 adds biometric step-up and TOTP for high tiers. Phase 3 moves toward passkeys once Supabase support is stable enough for production.

09 / Decision 3: The Three Questions

The three cards decide whether onboarding becomes product-market-fit infrastructure.

The research is clear: never ask plainly for wealth, status, or usefulness. Ask about season, standards, absences, offers, and access.

Set A

Frequencies -> Absences -> Standards

  • Where did your time concentrate?
  • What was hardest to find this year?
  • What would meet your standard?
Decision analysis
  • Best sponsor signal because standards map to premium categories without asking spend.
  • Strong investor signal because absences reveal unmet demand.
  • Most editorial and least extractive, but takes more design and interaction work.
Set B

Role -> Stage -> 90-day Essential

  • Which best describes your role?
  • What stage is your current build?
  • What would make AMARI essential in 90 days?
Decision analysis
  • Best for clean segmentation and investor storytelling.
  • Fastest to implement as card selections.
  • Less premium and less subtle than Set A.
Set C

Stage -> Offer -> Ask

  • What are you advancing this season?
  • Where could you create value?
  • What would make AMARI useful now?
Decision analysis
  • Best for resource graph seeding because it captures both supply and demand.
  • Strong for matching and first recommendations.
  • Riskier if "create value" feels like AMARI is extracting from the member.
Recommended decision: use a hybrid: Premium D3 voice, D4's Stage/Offer/Ask structure, and D1's "Absences"/"Standards" language where sponsor signal matters. This gives useful data without making members feel surveyed for monetization.
10 / Decision 4: Field-Level Encryption

How much encryption complexity should AMARI take on immediately?

Option A

pgcrypto + Vault-stored key

Encrypt structured high-sensitivity fields inside Postgres using keys pulled from Supabase Vault.

Tradeoff
  • Upside: backup leaks expose ciphertext for the most sensitive fields.
  • Upside: strong pattern for phone, address, financial bands, and self-declared sensitive info.
  • Downside: harder RLS/view design and more operational complexity.
Option B

Application-layer envelope encryption with KMS

Use AWS/GCP/HashiCorp KMS style key hierarchy and encrypt before database writes.

Tradeoff
  • Upside: strongest institutional-grade key separation.
  • Upside: good for future sponsor due diligence.
  • Downside: over-complex for current Supabase-only app and slows shipping.
Option C

Supabase Vault + app-layer encryption for sensitive free text

Keep secrets in Vault, avoid pgsodium, encrypt only narrow sensitive data paths in v1.

Tradeoff
  • Upside: easiest to ship safely now.
  • Upside: aligns with Supabase direction and avoids deprecated pgsodium work.
  • Downside: does not give full column encryption coverage immediately.
Recommended decision: Option C for v1. Add pgcrypto for structured high-sensitivity fields in Phase 2. Defer full KMS envelope encryption until institutional due diligence demands it.
11 / Decision 5: Attestation and Anti-Tamper

Device trust should influence risk, not become a brittle single gate.

freeRASP

Root/jailbreak, debugger, Frida, emulator, sideload, and binary-tamper detection.

  • Good as defence-in-depth.
  • Can produce false positives and UX friction.
  • Client-side checks can be bypassed by skilled attackers.

App Attest + Play Integrity

Hardware/platform-backed attestation validated server-side before sensitive actions.

  • Most trustworthy device signal.
  • Should gate exports, intros, invite redemption, and directory access.
  • Some devices may not support every verdict.

@expo/app-integrity

Expo-friendly wrapper, alpha status, best as pilot path for high-value calls.

  • Fastest Expo SDK 54 integration.
  • Needs graceful fallback.
  • Do not hard-block unsupported devices at first.

Tiered response model

Low risk: allow normal reads. Medium risk: require biometric step-up or restrict sensitive features. High risk: block exports/sensitive mutations, revoke session, and alert admin. This avoids punishing legitimate members while still reducing blast radius.

12 / Decision 6: Resource Graph Storage

The graph should be an evidence ledger, not a hidden human-value score.

Option A

Single denormalized resource profile

One row per member with score columns and confidence fields.

Tradeoff
  • Upside: simple reads and simple matching queries.
  • Downside: hard to audit why a score changed.
  • Downside: easier to drift into hidden ranking behavior.
Option B

Evidence ledger rows

Every signal is a row with dimension, source, confidence, expiry, visibility, and consent scope.

Tradeoff
  • Upside: auditable, reversible, time-decayed, and privacy-defensible.
  • Downside: more tables and snapshot jobs.
Option C

Hybrid ledger + materialized snapshot

Ledger is source of truth. Snapshot or materialized view supports matching and dashboards.

Tradeoff
  • Upside: best balance of auditability and performance.
  • Upside: lets AMARI explain every inference later.
  • Downside: requires more disciplined schema and jobs from the start.
Recommended decision: Option C. Self-declared onboarding signals set the prior; verified behavior strengthens confidence over time. Never expose individual scores to partners.
13 / Investor and Sponsor Reporting

AMARI can tell the commercial story without exposing members.

The sponsor/investor promise is aggregate intelligence: who the community is, what it is building, what it can contribute, and what it needs. Never individual drill-through.

Allowed

  • Counts and percentages by cohort.
  • Archetype and stage mix.
  • Offer/ask demand patterns.
  • Resource activation rate.
  • Event conversion and retention trends.

Not allowed

  • Named exports.
  • Member-level rows.
  • Hidden "VIP" or "high net worth" labels.
  • Precise location histories.
  • Sponsor drill-through into profiles.

North star

Resource activation rate: the share of onboarded members who complete at least one meaningful ecosystem action in a time window.

Threshold Use Case Reasoning
k >= 3 Internal map/geographic degradation Enough to reduce individual doxxing risk for coarse public-like product surfaces.
k >= 20 Partner/investor reporting Commercial pressure to identify individuals is higher; reporting must remain cohort-safe.
14 / Roadmap

Do the critical security work before wider invite distribution.

Phase 0: Pre-flight audit

Run the section14 audit against the repo: RLS, service-role keys, Mapbox tokens, EAS Update signing, Supabase region, monitoring SDKs, and SDK budget.

Phase 1: Critical two-week sprint

RLS coverage, locked security-definer functions, invite-code hardening, service-role audit, Mapbox token audit, OTP hardening, screen/log privacy, EAS Update code signing, privacy policy surfaces, incident runbook.

Phase 2: 60-day hardening

Certificate pinning, app integrity, MFA, refresh-token rotation, field-level encryption, k-anonymity map, audit logs, active sessions, data export/delete, SBOM, first pen-test scoping, resource graph v1.

Phase 3: 90-180 days

SOC 2 readiness, external pen test, private bug bounty, quarterly access reviews, WAF/rate limiting, vendor security reviews, anomaly detection, privacy-safe export workflow.

15 / Founder Decisions

The decisions to make before Codex starts building the next PR stack.

Recommended choices

  • Auth: PKCE email OTP for MVP, biometric/MFA Phase 2, passkeys Phase 3.
  • Graph: Builder <-> Disruptor x Operator <-> Connector for v1, extensible to six-axis later.
  • Questions: premium hybrid using season, offer, ask, absences, and standards.
  • Encryption: Vault/app-layer v1, pgcrypto Phase 2, KMS only for institutional due diligence.
  • Attestation: `@expo/app-integrity` pilot for sensitive calls, freeRASP later.
  • Resource graph: evidence ledger + materialized snapshot.

Non-negotiable gates

  • No wider invite distribution until RLS audit passes.
  • No EAS Updates in production without code signing.
  • No sensitive logs, screen replay, or raw gesture trails in onboarding.
  • No partner reporting below cohort thresholds.
  • No service-role key in anything bundled to iOS or Android.
  • No hidden "member value" score.
If AMARI is trusted with the map of a premium diaspora network, the product must behave like a fiduciary of that network.
